# ReviewLens 架构设计说明书

> 版本：1.0 | 日期：2026-09-02 | 状态：待评审\
> 前置文档：[01-需求分析说明书](01-需求分析说明书.md)

## 1. 设计目标

ReviewLens 的架构设计围绕三个核心原则：

1. **可追溯**：每个聚合指标可回查到原始评论、模型版本和数据集版本
2. **可复现**：相同数据 + 种子 + 代码 → 相同指标，新人可独立启动
3. **可演进**：基线模型可被 BERT 替换而不改业务代码，NLP 服务独立扩缩容

### 2.1 组件职责

| 组件            | 职责               | 不做的事           |
| ------------- | ---------------- | -------------- |
| Frontend      | 展示状态、提交表单、筛选数据   | 不在前端计算指标，不绕过权限 |
| Backend       | 领域接口、事务、鉴权、审计、编排 | 不直接执行长时间模型训练   |
| PostgreSQL    | 结构化领域数据和状态       | 不存放大文件或模型权重    |
| Elasticsearch | 评论全文索引和聚合        | 不作为业务事实的唯一来源   |
| Redis + ARQ   | 异步导入、批量推理、短期状态   | 不作为唯一事实来源      |
| MinIO         | 原始文件、拒绝报告、模型产物   | 不替代数据库的状态记录    |
| NLP Service   | 预处理、训练、评测、推理     | 不直接修改业务问题卡     |

### 2.2 进程模型

```text
本地开发：
  Docker Compose 启动 4 个基础设施容器（PG, ES, Redis, MinIO）
  + 本地 Python 进程：FastAPI (uvicorn) + ARQ Worker + NLP Service (uvicorn)
  + 本地 Node 进程：Vite Dev Server

生产部署：
  Docker Compose 启动全部 7 个容器
  或拆分为 K8s 集群（超出本期范围）
```

## 3. 技术选型与对比分析

以下每项技术选型都包含：**为什么选它、对比了什么、为什么不选其他、简历可讲什么**。

### 3.1 后端框架：FastAPI

| 维度     | FastAPI             | Django REST       | Flask + Flask-RESTful | Spring Boot           |
| ------ | ------------------- | ----------------- | --------------------- | --------------------- |
| 异步支持   | 原生 async/await      | 部分支持（ASGI）        | 需 async 扩展            | 原生（WebFlux）           |
| API 文档 | 自动 OpenAPI 3.1      | 需 drf-spectacular | 需 flasgger            | 需 springdoc           |
| 类型安全   | Pydantic v2 原生      | 无（需 Serializer）   | 无                     | JPA + Bean Validation |
| ML 集成  | Python 原生，直接 import | Python 原生         | Python 原生             | 需跨语言调用                |
| 性能     | Starlette ASGI，高    | 中                 | 中                     | 高（JIT）                |
| 学习曲线   | 低（Python 装饰器）       | 中（ORM + 序列化）      | 低                     | 中高（Spring 体系）         |

**选择 FastAPI 的理由**：

1. NLP 服务和业务 API 同为 Python，无需跨语言调用，模型对象可直接传递
2. Pydantic v2 提供编译时类型检查，请求/响应 schema 即代码即文档
3. 异步原生支持——批量 NLP 推理不阻塞 API 请求
4. 自动 OpenAPI 文档——简历可讲"API 契约与实现零漂移"

**为什么不选 Django REST**：Django 的 ORM 和 Admin 对本项目是负担（我们用 SQLAlchemy 2.0 + Alembic），且 DRF 的序列化层与 Pydantic 重复。Flask 过于裸露需要大量中间件搭建。

### 3.2 ORM 与迁移：SQLAlchemy 2.0 + Alembic

| 维度    | SQLAlchemy 2.0             | Django ORM         | Tortoise ORM |
| ----- | -------------------------- | ------------------ | ------------ |
| 类型安全  | Mapped\[T] + typed session | 无原生类型提示            | Pydantic 集成  |
| 异步    | AsyncSession 原生            | 部分支持               | 原生           |
| 迁移    | Alembic（可审查 SQL）           | makemigrations（黑盒） | Aerich       |
| 复杂查询  | Core + ORM 双层              | ORM only           | ORM only     |
| 数据库支持 | 多后端                        | 仅优化 PostgreSQL     | 多后端          |

**选择理由**：

1. SQLAlchemy 2.0 的 `Mapped[T]` 类型注解让 IDE 补全和 mypy 检查可用
2. Alembic 生成的迁移脚本是纯 SQL，可审查、可回滚、可重复执行
3. Core 层可写复杂聚合查询（看板的属性×时间×SKU 三维聚合），ORM 层处理 CRUD

**简历可讲**："使用 SQLAlchemy 2.0 类型安全 ORM + Alembic 迁移管理，实现领域模型与数据库 schema 的可审查同步"

### 3.3 数据库：PostgreSQL 16

| 维度      | PostgreSQL 16           | MySQL 8         | SQLite      |
| ------- | ----------------------- | --------------- | ----------- |
| JSON 操作 | JSONB + GIN 索引，原生操作符    | JSON 类型，索引弱     | JSON1 扩展，基本 |
| 窗口函数    | 完整支持（RANGE/ROWS/GROUPS） | 基本支持            | 基本支持        |
| CTE 递归  | WITH RECURSIVE          | WITH（8.0+）      | WITH        |
| 全文检索    | tsvector + GIN（内置中文支持弱） | FULLTEXT（不支持中文） | FTS5        |
| 向量扩展    | pgvector（AI 向量检索）       | 无原生             | 无           |
| 并发      | MVCC，写不阻塞读              | InnoDB MVCC     | WAL         |
| 分区表     | 声明式分区                   | InnoDB 分区       | 无           |

**选择理由**：

1. **JSONB + GIN 索引**：审核任务的 `aspects_json` 和训练运行的 `metrics_json` 需要 JSON 查询，PostgreSQL 的 JSONB 操作符（`->>`, `@>`, `?`）和 GIN 索引让 JSON 字段查询性能接近结构化字段
2. **窗口函数**：看板的"属性差评率环比变化"需要 `LAG() OVER (PARTITION BY aspect, product_id ORDER BY period)`，PostgreSQL 的窗口函数完整且高效
3. **pgvector**：后续 NLP 向量检索（评论相似度、语义搜索）可直接用 PostgreSQL，不需要额外引入向量数据库
4. **声明式分区**：评论表按月分区，10 万+ 数据查询可分区裁剪

**为什么不选 MySQL**：JSON 索引弱（JSON 字段无法建 GIN），窗口函数功能不全（缺少 GROUPS 帧），无向量扩展。SQLite 不适合多进程写入。

**简历可讲**："基于 PostgreSQL 16 的 JSONB + GIN 索引优化审核标签查询，使用窗口函数实现属性差评率趋势环比计算，pgvector 预留语义检索能力"

### 3.4 全文搜索引擎：Elasticsearch 8 + IK 分词器

| 维度   | Elasticsearch 8                   | PostgreSQL FTS  | Meilisearch | Typesense |
| ---- | --------------------------------- | --------------- | ----------- | --------- |
| 中文分词 | IK 插件（ik\_max\_word）              | 内置差（需 zhparser） | 内置支持        | 内置支持      |
| 聚合   | 完整（terms, date\_histogram, stats） | 基本聚合            | 基础          | 基础        |
| 数据量  | 百亿级                               | 十万级             | 百万级         | 百万级       |
| 实时索引 | 近实时（1s refresh）                   | 实时              | 实时          | 实时        |
| 高亮   | 原生 highlight                      | 无               | 内置          | 内置        |
| 分面搜索 | terms 聚合                          | 无原生             | 内置          | 内置        |

**选择理由**：

1. **10 万+ 评论全文搜索**：评论正文需要按关键词、短语搜索，PostgreSQL 的 LIKE 查询在这个数据量下性能不足
2. **中文分词**：IK 分词器是 Elasticsearch 中文搜索的事实标准，ik\_max\_word 模式细粒度分词适合评论搜索
3. **聚合分析**：看板的"按属性/情感/评分/时间的分面统计"直接用 Elasticsearch 的 terms + date\_histogram 聚合，无需在应用层计算
4. **高亮**：搜索结果中关键词高亮是前端展示的硬需求

**为什么不选 PostgreSQL FTS**：tsvector 对中文支持差（需第三方 zhparser 扩展），聚合能力远不如 Elasticsearch，无高亮功能。Meilisearch/Typesense 在聚合能力和数据量上不足。

**简历可讲**："使用 Elasticsearch 8 + IK 分词器构建评论全文索引，支持 10 万+ 评论的中英文混合搜索和实时分面聚合，p95 延迟 < 500ms"

### 3.5 前端框架：React 18 + TypeScript + Vite + Ant Design 5

| 维度    | React 18              | Vue 3           | Svelte      | Angular                   |
| ----- | --------------------- | --------------- | ----------- | ------------------------- |
| 市场占有率 | \~40%（最高）             | \~18%           | \~4%        | \~17%                     |
| 类型安全  | TypeScript 原生         | Vue + TS（Volar） | Svelte + TS | TypeScript 原生             |
| 生态规模  | 最大（npm 包）             | 大               | 中           | 大                         |
| 学习曲线  | 中                     | 低               | 低           | 高                         |
| 企业级组件 | Ant Design 5（最成熟）     | Ant Design Vue  | 无成熟方案       | Material/Angular Material |
| 性能    | Concurrent + Suspense | 响应式             | 编译优化        | Zone.js                   |
| 构建工具  | Vite（快）               | Vite            | Vite        | webpack/ esbuild          |

**选择理由**：

1. **市场占有率**：React 在国内和国际市场的岗位需求量远超其他框架，简历认知度最高
2. **TypeScript 集成**：React + TS 是行业标准，类型安全对复杂状态管理（筛选条件×时间窗口×属性维度）至关重要
3. **Ant Design 5**：企业级组件库最成熟，Table（审核队列）、Form（导入配置）、Charts（看板趋势）都有开箱即用的高质量实现
4. **Vite 构建**：开发热更新 < 100ms，生产构建 Tree-shaking 好

**为什么不选 Vue 3**：虽然 Vue 3 也在改进 TS 支持，但 React 的生态规模、社区资源和岗位数量明显更大。旧项目用 Vue 是因为 JeecgBoot 框架绑定，脱离框架后没有理由继续用 Vue。

**简历可讲**："基于 React 18 + TypeScript + Ant Design 5 构建评论分析工作台，实现属性级看板、审核队列和问题卡状态机的复杂状态管理"

### 3.6 异步任务队列：Redis + ARQ

| 维度           | ARQ             | Celery                | RQ | Dramatiq |
| ------------ | --------------- | --------------------- | -- | -------- |
| 异步模型         | asyncio 原生      | 线程/进程                 | 线程 | 线程/进程    |
| 与 FastAPI 集成 | 天然（同 asyncio）   | 需配置                   | 一般 | 一般       |
| 依赖           | 轻（仅 redis）      | 重（需 broker + backend） | 轻  | 中        |
| 任务追踪         | 原生 result store | flower + backend      | 简单 | 中等       |
| 定时任务         | 无（可用 cron）      | beat scheduler        | 无  | 无        |
| 学习曲线         | 低               | 中                     | 低  | 中        |

**选择理由**：

1. **asyncio 原生**：ARQ 与 FastAPI 共享同一事件循环，NLP 批量推理是 I/O 密集型（调用 NLP 服务 HTTP 接口），asyncio 模型效率最高
2. **轻量**：不需要额外的 broker（Celery 需要 RabbitMQ 或 Redis 作为 broker + backend），ARQ 只需 Redis
3. **类型安全**：ARQ 的任务定义使用 Python 类型注解，与 Pydantic 级别的类型检查一致

**为什么不选 Celery**：Celery 是线程模型，与 FastAPI 的 asyncio 不在同一线程模型，混用需额外处理。Celery 的配置复杂度（broker + backend + flower + beat）对个人项目过重。

**简历可讲**："使用 ARQ asyncio 异步任务队列处理评论批量导入和 NLP 推理任务，与 FastAPI 共享事件循环实现零额外 broker 依赖"

### 3.7 NLP 技术栈：scikit-learn + jieba + transformers

| 层    | 库                    | 用途             | 选型理由                     |
| ---- | -------------------- | -------------- | ------------------------ |
| 分词   | jieba                | 中文分词           | 事实标准，支持自定义词典             |
| 基线模型 | scikit-learn         | TF-IDF + LR    | 可解释、可复现、不依赖 GPU          |
| 进阶模型 | transformers + torch | BERT 微调        | HuggingFace 生态最大，预训练模型最多 |
| 评测   | scikit-learn metrics | F1, 混淆矩阵, 分类报告 | 标准评测工具链                  |

**分层策略**：基线模型不依赖 GPU 和深度学习框架，任何环境可复现。进阶模型在有足够标注数据后按需启用，不阻塞主链路。

### 3.8 对象存储：MinIO

| 维度     | MinIO             | 本地文件系统 | S3  |
| ------ | ----------------- | ------ | --- |
| S3 兼容  | 是                 | 不适用    | 原生  |
| 版本管理   | bucket versioning | 手动     | 原生  |
| Docker | 一键                | 不适用    | 云服务 |
| 多实例    | 支持                | 不支持    | 支持  |
| 生产迁移   | 零代码改 S3           | 需重写    | 原生  |

**选择理由**：原始 CSV/JSONL 文件和模型产物不能放数据库（太大），也不能散落在服务器目录（不可追溯、多实例不共享）。MinIO 在本地提供 S3 兼容 API，生产部署时改 endpoint 即可迁移到 AWS S3 或阿里云 OSS，代码零修改。

### 3.9 CI/CD：GitHub Actions

| 维度   | GitHub Actions | GitLab CI    | Jenkins            |
| ---- | -------------- | ------------ | ------------------ |
| 集成   | GitHub 原生      | GitLab 原生    | 需独立部署              |
| 配置   | YAML in repo   | YAML in repo | Groovy/Jenkinsfile |
| 免费额度 | 2000 min/月     | 400 min/月    | 无                  |
| 缓存   | actions/cache  | cache        | 插件                 |
| 矩阵构建 | matrix         | parallel     | matrix             |

**选择理由**：项目托管在 GitHub，CI 与代码同仓库。YAML 配置即代码，可审查。免费额度够用（测试 + 构建约 10 分钟/次）。

### 7.1 API 前缀与规范

+ 所有业务 API 前缀：`/api/v1`

+ 认证 API 前缀：`/api/auth`

## 8. 安全设计

| 类别     | 措施                                  | 实现                         |
| ------ | ----------------------------------- | -------------------------- |
| 密码存储   | bcrypt 哈希（不使用 DES/AES 可逆加密）         | passlib                    |
| JWT 签名 | 独立密钥（环境变量注入），不用用户密码                 | python-jose                |
| API 鉴权 | 所有业务接口挂 `Depends(get_current_user)` | FastAPI dependency         |
| CORS   | 白名单 origin，不使用正则通配                  | FastAPI middleware         |
| 密钥管理   | 所有密钥通过 `.env` 注入，缺失时启动失败            | Pydantic Settings          |
| 文件上传   | 限制类型（.csv/.jsonl）和大小（100MB）         | FastAPI UploadFile         |
| SQL 注入 | SQLAlchemy 参数化查询，不拼接 SQL            | SQLAlchemy ORM             |
| 审计日志   | 关键操作记录用户、对象、动作、时间                   | middleware + audit\_logs 表 |
| 数据脱敏   | reviewer\_id 脱敏后存储，不返回密码/密钥         | 字段过滤                       |

## 12. 设计决策记录

| 决策    | 选择              | 备选                   | 理由                               |
| ----- | --------------- | -------------------- | -------------------------------- |
| 后端框架  | FastAPI         | Django REST, Flask   | Python + async + 自动文档 + ML 原生    |
| ORM   | SQLAlchemy 2.0  | Django ORM, Tortoise | 类型安全 + Alembic 可审查迁移 + Core 复杂查询 |
| 数据库   | PostgreSQL 16   | MySQL 8              | JSONB + 窗口函数 + pgvector          |
| 搜索    | Elasticsearch 8 | PG FTS, Meilisearch  | 中文分词 + 聚合 + 高亮 + 10万+ 数据量        |
| 前端    | React 18 + TS   | Vue 3, Svelte        | 市场占有率 + 类型安全 + Ant Design 5      |
| 任务队列  | ARQ             | Celery, RQ           | asyncio 原生 + 轻量 + 无额外 broker     |
| 对象存储  | MinIO           | 本地文件, S3             | S3 兼容 + Docker + 多实例 + 零代码迁移     |
| CI/CD | GitHub Actions  | GitLab CI, Jenkins   | GitHub 原生 + YAML + 免费额度          |
