# ReviewLens 需求分析说明书

> 版本：1.0 | 日期：2026-09-02 | 状态：待评审

## 1. 项目定位

### 1.1 一句话定位

> ReviewLens 是面向电商品牌运营的商品评论体验分析平台——从 10 万条评论中自动提取"续航差评涨了 40%"这样的属性级信号，追踪趋势，触发预警，并将洞察转化为可验证的产品改进闭环。

### 1.2 项目背景

电商品牌团队每天收到大量商品评论，但评论往往只被当作评分存档。运营无法迅速发现"电池续航"或"包装破损"何时恶化，也难以证明一次产品改版是否改善了用户体验。简单的"好评率 87%"不能支持行动决策。

现有方案的缺口：

| 现有方案                     | 做了什么       | 缺什么                  |
| ------------------------ | ---------- | -------------------- |
| 电商平台内置（淘宝/京东/Amazon）     | 评分分布、关键词高亮 | 属性级情感、趋势预警、问题闭环      |
| SaaS 工具（Revuze/Thematic） | 属性抽取、自动洞察  | 黑盒不可复现、无法自部署、不连接行动流程 |
| 手动分析（Excel/Tableau）      | 透视、图表      | 无法处理文本语义、不可扩展、无法自动化  |

ReviewLens 的定位是填补"从分析到行动"的缺口：不只告诉运营"问题在哪"，还帮他们"创建问题卡→分派→处置→验证→关闭→效果回测"。

### 1.3 产品边界

**ReviewLens 负责：**

- 真实电商评论数据的导入、质量校验和版本化

- 评论全文索引和多维检索

- 属性级情感分析（Aspect-Based Sentiment Analysis）

- 体验趋势追踪和异常预警

- 人工审核工作流和模型质量管控

- 问题卡全生命周期管理（创建→分派→处置→验证→关闭→效果回测）

- 数据导出

**ReviewLens 不负责：**

- 电商评论的自动爬取（数据来自公开数据集或用户上传）

- 消费者身份信息的存储和处理

- 自动商品下架或赔付决策

- 外部系统（ERP/CRM/Jira）的直接对接

- 多租户和商业化计费

- 没有独立评测集的 BERT 生产发布

### 1.4 简历表达边界

推荐表述：

> ReviewLens｜商品评论体验分析平台｜全栈开发
> 面向电商品牌运营场景，基于 React + FastAPI + PostgreSQL + Elasticsearch 构建评论属性级情感分析、趋势预警和问题闭环系统。基于 Amazon Reviews 2023 公开数据集（X 万条），实现 \[指标]。

必须使用仓库中真实运行产出的指标，不写"海量实时分析""生产上线""BERT 准确率 92%"等未经独立评测证明的内容。

## 2. 目标用户与角色

### 2.1 用户角色与核心任务

| 角色    | 核心任务              | ReviewLens 提供的价值   |
| ----- | ----------------- | ------------------ |
| 品牌运营  | 找出 SKU 本月最严重的体验问题 | 属性差评率排行 + 证据评论     |
| 品类负责人 | 对比商品/版本/渠道体验差异    | 统一口径的多维对比          |
| 产品研发  | 接收具体问题并验证修复效果     | 问题卡 + 改版前后差评率对比    |
| 数据分析师 | 验证数据和模型质量         | 导入报告 + 审核样本 + 评测指标 |
| 管理者   | 了解问题规模和处理进度       | 汇总视图 + 问题卡看板       |

### 2.2 权限模型

一期采用三角色 + 管理员：

| 角色  | 数据导入     | 审核    | 训练    | 问题卡      | 系统管理 |
| --- | -------- | ----- | ----- | -------- | ---- |
| 运营  | 查看、导入    | 编辑    | 查看    | 创建、分派、验证 | 无    |
| 分析师 | 查看、导入、导出 | 审核、复核 | 创建、评测 | 查看       | 无    |
| 管理员 | 全部       | 全部    | 全部    | 全部       | 用户管理 |

更细粒度的数据范围控制（按团队/类目/品牌隔离）属于后续迭代。

## 3. 数据源

### 3.1 主数据源

**Amazon Reviews 2023 Dataset（McAuley Lab, UCSD）**

| 属性   | 值                                        |
| ---- | ---------------------------------------- |
| 发布地址 | <https://amazon-reviews-2023.github.io/> |
| 许可   | 学术研究用途                                   |
| 总规模  | 全品类 5 亿+ 条                               |
| 选取品类 | Electronics（电子产品）、Home & Kitchen（家居厨房）   |
| 子集规模 | 10 万 - 50 万条（按需选取）                       |
| 格式   | JSON Lines                               |

### 3.2 数据字段映射

| 原始字段               | ReviewLens 字段      | 类型       | 说明                |
| ------------------ | ------------------ | -------- | ----------------- |
| rating             | rating             | int      | 1-5 星评分           |
| title              | review\_title      | string   | 评论标题              |
| text               | review\_text       | text     | 评论正文（核心分析对象）      |
| asin               | product\_id        | string   | 商品 ASIN           |
| parent\_asin       | product\_group\_id | string   | 商品组 ID（同款不同颜色/规格） |
| user\_id           | reviewer\_id       | string   | 评论者 ID（脱敏）        |
| timestamp          | reviewed\_at       | datetime | 评论时间戳             |
| helpful\_vote      | helpful\_votes     | int      | 有用投票数             |
| verified\_purchase | verified\_purchase | bool     | 是否验证购买            |

### 3.3 数据分层

| 层          | 内容               | 存储位置                       | 可否提交 Git |
| ---------- | ---------------- | -------------------------- | -------- |
| seed       | 数据集元信息和下载脚本      | 仓库                         | 可以       |
| raw        | 原始 JSON Lines 文件 | MinIO                      | 不可以      |
| normalized | 规范化评论记录          | PostgreSQL + Elasticsearch | 不可以      |
| reviewed   | 人工审核结论           | PostgreSQL                 | 不可以      |
| model      | 模型文件和评测指标        | MinIO + PostgreSQL         | 不可以      |

### 3.4 数据保留原则

- 原始评论和规范化记录不可覆盖更新

- 修正标签通过审核记录更新，不修改原评论

- 不存储消费者真实身份信息（user\_id 脱敏后存储）

- 删除真实数据需管理员审批，一期不提供物理删除接口

## 4. 功能需求

### 4.1 数据导入与版本化

**目标**：将不同来源的评论文件转换为统一、可追溯的版本化数据集。

**支持格式**：

- JSON Lines（Amazon Reviews 原始格式）

- CSV（标准字段 + 常见别名 + 显式映射）

**校验规则**：

| # | 规则                                                       | 失败处理                  |
| - | -------------------------------------------------------- | --------------------- |
| 1 | 文件不能为空                                                   | 拒绝导入                  |
| 2 | 必填字段：review\_id, product\_id, review\_text, reviewed\_at | 返回缺失字段列表              |
| 3 | review\_id 同一数据集内唯一                                      | 重复行进入拒绝报告             |
| 4 | review\_text 非空，长度 1-5000 字符                             | 空文本或超长行进入拒绝报告         |
| 5 | reviewed\_at 可解析为有效时间戳                                   | 格式错误行进入拒绝报告           |
| 6 | rating 如果存在，为 1-5 的整数                                    | 非法值进入拒绝报告             |
| 7 | 识别语言标记（中文/英文/混合）                                         | 记录在规范化结果中             |
| 8 | 多余字段保留但记录质量提示                                            | 不禁用，标注为额外列            |
| 9 | 重复文件（相同 SHA-256 + 映射）                                    | 返回已有版本，标记 reused=true |

**输出**：

- `dataset_version`：不可变版本号

- 文件 SHA-256 校验和

- 字段映射记录

- 质量报告：有效行数、拒绝行数、拒绝原因统计

- 规范化评论记录写入 PostgreSQL 和 Elasticsearch

**验收标准**：

1. 给定 10 万条 Amazon Reviews JSONL，系统在 5 分钟内完成导入（异步任务）
2. 部分行错误时，有效行进入版本，拒绝行有可解释报告
3. 重复导入返回 `reused=true`，不重复插入
4. 导入完成后 Elasticsearch 索引可检索

### 4.2 评论搜索引擎

**目标**：支持对 10 万+ 评论进行全文检索和聚合分析。

**功能清单**：

| # | 功能   | 说明                                     |
| - | ---- | -------------------------------------- |
| 1 | 全文搜索 | 关键词、短语、布尔表达式                           |
| 2 | 中文分词 | IK 分词器（ik\_max\_word）                  |
| 3 | 多维筛选 | product\_id、category、rating 范围、时间范围、语言 |
| 4 | 分面聚合 | 按属性、情感、评分、时间的分面统计                      |
| 5 | 排序   | 相关度、时间、有用投票数                           |
| 6 | 高亮   | 搜索词在评论原文中高亮                            |
| 7 | 分页   | 每页 20 条，支持深翻页                          |

**验收标准**：

1. 10 万条评论全文搜索响应时间 < 500ms（p95）
2. 聚合查询返回属性分布、情感分布、时间趋势
3. 支持中英文混合搜索

### 4.3 NLP 分析管线

**目标**：从评论文本中提取属性级情感信号。

**分析阶段**：

| 阶段     | 输入      | 输出                                   | 方法                        |
| ------ | ------- | ------------------------------------ | ------------------------- |
| 文本预处理  | 原始评论    | 清洗后文本 + 语言标记                         | 规则 + jieba 分词             |
| 属性抽取   | 清洗文本    | 属性列表（如"续航""充电""包装"）                  | 受控词表 + 规则匹配               |
| 情感分类   | 清洗文本    | 情感标签（positive/neutral/negative）+ 置信度 | TF-IDF + LR（基线）/ BERT（进阶） |
| 属性情感关联 | 属性 + 情感 | 属性×情感矩阵                              | 句法距离 + 规则关联               |

**属性词表**（受控，不可自由文本）：

一期覆盖电子产品核心体验维度：

| 属性   | 典型关键词                   |
| ---- | ----------------------- |
| 电池续航 | battery,续航,电池,电量,充电一次   |
| 充电速度 | charge,充电速度,快充,慢充       |
| 屏幕显示 | screen,屏幕,显示,分辨率,色彩     |
| 性能速度 | performance,性能,卡顿,流畅,速度 |
| 音质   | sound,音质,噪音,声音,扬声器      |
| 外观设计 | design,外观,设计,颜值,做工      |
| 包装   | packaging,包装,破损,盒子      |
| 售后服务 | service,售后,客服,退换,维修     |
| 价格价值 | price,价格,性价比,贵,划算       |
| 物流配送 | delivery,物流,快递,发货,配送    |
| 可靠性  | quality,质量,故障,坏,维修      |
| 安全性  | safe,安全,发热,起火,烫         |

**输出记录**：

- 每条评论的预测结果包含：属性列表、每属性情感、整体情感、置信度

- 预测结果绑定数据集版本和模型版本

- 置信度 < 0.7 的样本自动进入审核队列

**验收标准**：

1. 属性抽取覆盖率：至少 60% 的评论能识别出至少一个产品属性
2. 情感分类准确率：基线模型 Macro-F1 >= 0.70（独立测试集）
3. 每条预测可追溯到模型版本和数据集版本
4. 批量推理 10 万条评论在 30 分钟内完成（异步任务）

### 4.4 人工审核工作流

**目标**：通过人工审核提高标签质量，为模型训练提供可信标注。

**审核任务来源**：

| 来源       | 策略                | 占比    |
| -------- | ----------------- | ----- |
| 低置信度预测   | 置信度 < 0.7         | \~30% |
| 负面+高风险属性 | 负面预测且命中可靠性/安全性/售后 | \~20% |
| 分层随机抽样   | 按 SKU、月份、情感类别分层   | \~50% |

**审核界面内容**：

不可修改的证据区：

- 原始评论文本、商品 ID、评论时间、渠道、评分

- 系统预测：属性列表、每属性情感、整体情感、置信度、模型版本、数据集版本

可编辑的审核区：

- 人工情感标签（positive/neutral/negative）

- 人工属性标签（从受控词表多选）

- 审核理由（受控标签）：

  - `confirm_prediction`：确认系统预测

  - `correct_sentiment`：修正情感

  - `correct_aspects`：修正属性

  - `correct_both`：同时修正情感与属性

  - `invalid_text`：无效文本

  - `insufficient_info`：信息不足

- 审核备注（可选文本）

**审核历史**：

- 保留每次审核的版本记录

- 支持二次复核和分歧标记

- 审核一致率和覆盖率进入质量报告

**验收标准**：

1. 审核人员可在连续队列中完成审核，无需复制 ID
2. 每条审核记录可追溯"谁、何时、基于什么证据、做了什么修正"
3. 审核结果与训练数据严格隔离，只有 `approved`/`verified` 进入训练
4. 审核状态机：

```text
pending → approved
pending → verified
pending → rejected
approved → verified
approved/verified → rejected（发现文本无效时）
```

### 4.5 模型训练与评测

**目标**：建立可复现、有发布门槛的模型训练管线。

**训练运行流程**：

```text
指定 dataset_version
    → 查询 approved/verified 审核样本
    → 校验最低样本数（>= 200 条）
    → 构建训练记录（train/test split 80/20）
    → 调用 NLP 服务训练
    → 回写指标、混淆矩阵、分类报告
    → 判定发布门槛
```

**模型版本管理**：

| 字段                     | 说明                                      |
| ---------------------- | --------------------------------------- |
| model\_version         | 不可变版本号                                  |
| dataset\_version       | 训练数据来源                                  |
| algorithm              | tfidf\_lr / bert\_base                  |
| random\_seed           | 固定随机种子                                  |
| train\_samples         | 训练样本数                                   |
| test\_samples          | 测试样本数                                   |
| macro\_f1              | 宏平均 F1                                  |
| accuracy               | 准确率                                     |
| classification\_report | 完整分类报告 JSON                             |
| confusion\_matrix      | 混淆矩阵 JSON                               |
| status                 | evaluation\_only / published / archived |
| model\_file\_sha256    | 模型文件校验和                                 |
| trained\_at            | 训练时间                                    |

**发布门槛**：

| 条件       | 阈值        |
| -------- | --------- |
| Macro-F1 | >= 0.70   |
| 独立测试样本   | >= 1000 条 |
| 人工审核覆盖率  | >= 80%    |

低于门槛的运行标记为 `evaluation_only`，不可作为生产模型。

**验收标准**：

1. 训练只使用 `approved`/`verified` 样本，未审核数据不可进入训练
2. 指标低于门槛时模型状态为 `evaluation_only`
3. 训练产物可独立复现（相同数据 + 种子 + 代码 = 相同指标）
4. 支持回滚到上一发布版本

### 4.6 体验洞察看板

**目标**：让运营在 3 分钟内定位当前最严重的体验问题。

**看板模块**：

| 看板     | 展示内容                 | 数据来源            |
| ------ | -------------------- | --------------- |
| 总览     | 评论总量、情感分布、审核进度、问题卡状态 | 聚合查询            |
| 属性排行   | 各属性差评率排行 + 环比变化      | NLP 预测聚合        |
| 趋势图    | 属性差评率时间序列（周/月粒度）     | NLP 预测 + 时间分组   |
| SKU 对比 | 同类目多 SKU 的属性差评率对比    | NLP 预测 + SKU 分组 |
| 证据下钻   | 聚合数字 → 评论原文列表        | Elasticsearch   |

**关键原则**：

- 每个聚合数字附带数据集版本、模型版本、筛选条件、生成时间

- 每个数字可点击下钻到支撑它的原始评论

- 不展示无法追溯来源的静态图表

**验收标准**：

1. 看板聚合数与明细评论数可互相核对
2. 同一 SKU 的时间窗口比较使用固定数据和模型版本
3. 每个指标可展开查看证据评论（至少 10 条）

### 4.7 问题卡管理

**目标**：将分析洞察转化为可追踪、可验证的改进行动。

**问题卡字段**：

| 字段                  | 类型       | 说明                                                 |
| ------------------- | -------- | -------------------------------------------------- |
| dataset\_version    | string   | 数据集版本                                              |
| title               | string   | 问题标题                                               |
| aspect              | enum     | 体验属性（受控词表）                                         |
| severity            | enum     | low / medium / high / critical                     |
| status              | enum     | open / in\_progress / pending\_validation / closed |
| description         | text     | 问题描述                                               |
| source\_review\_ids | json     | 来源评论 ID 列表                                         |
| assignee            | string   | 负责人                                                |
| resolution\_note    | text     | 处置说明                                               |
| validation\_note    | text     | 验证结论                                               |
| created\_by         | string   | 创建人                                                |
| updated\_at         | datetime | 最后更新时间                                             |

**状态机**：

```text
open → in_progress
in_progress → open
in_progress → pending_validation
pending_validation → in_progress
pending_validation → closed（必须填写验证结论）
closed → 终态，不可流转
```

**审计轨迹**：

- 每次状态变更记录：操作者、前后状态、原因、时间

- 来源评论必须属于问题卡声明的数据集版本

- 关闭后可回测：对比问题卡创建前后同属性的差评率变化

**验收标准**：

1. 问题卡不能跳过 `pending_validation` 直接关闭
2. 来源评论可回查到原始全文
3. 关闭后回测报告显示改版前后差评率对比

### 4.8 告警与导出

**告警规则**：

| 规则类型 | 条件                 | 示例             |
| ---- | ------------------ | -------------- |
| 阈值规则 | 属性差评率超过 X%         | "可靠性差评率 > 15%" |
| 趋势规则 | 属性差评率环比增长超过 X%     | "续航差评率环比 +40%" |
| 去重规则 | 同属性同 SKU 在 N 天内不重复 | 默认 7 天去重       |

告警状态：`active → acknowledged → resolved`

**数据导出**：

- 格式：CSV

- 内容：评论原文 + 预测结果 + 审核标签 + 数据集版本

- 记录：操作人、时间、范围、文件路径

## 5. 非功能需求

| 类别   | 要求                                                 | 验证方式    |
| ---- | -------------------------------------------------- | ------- |
| 性能   | API p95 < 200ms；全文搜索 p95 < 500ms；批量导入 10 万条 < 5 分钟 | 压测 + 日志 |

## 6. 验收标准

### P1 基础设施

1. Docker Compose 启动全部服务，健康检查通过
2. 用户可注册、登录、获得角色
3. 数据库迁移可重复执行（Alembic upgrade/downgrade）

### P2 数据闭环

1. Amazon Reviews JSONL 可导入并生成稳定版本
2. 导入后 Elasticsearch 可全文搜索
3. 质量报告可解释拒绝行
4. 重复导入返回 `reused=true`

### P3 分析闭环

1. NLP 管线可对 10 万条评论批量推理
2. 看板展示属性差评率排行和趋势
3. 每个聚合数字可下钻到评论原文
4. 模型训练有完整指标和发布门槛判定

### P4 运营闭环

1. 审核队列可连续完成
2. 问题卡可从创建到关闭完整流转
3. 告警规则可触发并去重
4. 关闭后可回测改版效果

### P5 工程交付

1. CI/CD 自动跑测试和构建
2. 新人 clone 后 Docker Compose 一键启动
3. 端到端测试通过固定演示数据
4. API 文档（OpenAPI）自动生成且与实现一致

## 7. 明确不做

- 不做电商评论自动爬虫

- 不做消费者身份信息存储

- 不做自动商品下架或赔付

## 8. 术语表

| 术语               | 定义                                |
| ---------------- | --------------------------------- |
| dataset\_version | 不可变的数据集版本号，由文件内容 SHA-256 + 字段映射生成 |
| 属性级情感分析          | 不仅判断评论整体情感，还判断每个产品属性的情感倾向         |
| 审核任务             | 从评论中抽样出来需要人工确认标签的任务               |
| 问题卡              | 从分析洞察创建的、需要分派和处置的业务事项             |
| 发布门槛             | 模型达到一定指标后才可发布为生产模型的规则             |
| 效果回测             | 问题卡关闭后，对比创建前后同属性差评率变化             |
| 置信度              | 模型预测的不确定性度量，低于阈值的进入审核队列           |
